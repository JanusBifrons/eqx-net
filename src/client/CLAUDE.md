# CLAUDE.md — src/client (Eyes and Ears)

`src/client` is everything the player sees and hears. It is **not** the source of truth — the server is. The client's job is to make latency invisible through prediction (Phase 3) and ghost projectiles (Phase 4), while deferring to server reality whenever the two disagree.

Read the root [CLAUDE.md](../../CLAUDE.md) for project-wide invariants before editing.

## Forbidden Imports (CI-enforced)

Never import from `src/client/`:

- Server-only networking: `colyseus` (the *server* Colyseus package; use `colyseus.js`)
- `@colyseus/ws-transport`
- Persistence / Node-only APIs: `better-sqlite3`, `express`, `pino`, `worker_threads`, `node:worker_threads`, `fs`, `node:fs`, `http`, `node:http`
- Anything under `src/server/**`

Allowed: `colyseus.js`, `react`, `react-dom`, `@mui/material`, `@emotion/*`, `pixi.js` v8, `pixi-viewport`, `howler`, `zustand`, `src/core`, `src/shared-types`.

## Zustand Purity (invariant #2, strictly enforced)

**No spatial fields may live in the Zustand store.** This is the single most important client-side rule.

- Forbidden keys (lint-blocked in `src/client/state/store.ts`): `x`, `y`, `vx`, `vy`, `angle`, `rotation`, `position`, `velocity`.
- What Zustand *is* for: `connectionStatus`, `sectorName`, `hullPct`, `ammo`, `sectorAlert`, `playerId`, dev-overlay toggles, HUD flags.
- What Zustand is *not* for: anything that updates every frame.

Why: Zustand triggers React re-renders on subscription changes. Putting per-frame spatial data in Zustand would cause 60 Hz React re-renders, which is a performance catastrophe. Spatial state lives in a plain-object render mirror that Pixi polls directly — no React involvement.

## Renderer Rules

- `PixiRenderer` implements `IRenderer` from `src/core/contracts/`.
- The renderer **polls** the state mirror every frame. It **never** subscribes to the event bus for positions. Lint blocks `bus.on` imports inside `src/client/render/`.
- Camera (`pixi-viewport`) follows the local ship. No global-space UI overlay in Pixi — HUD elements are React/MUI outside the Pixi surface.
- **Starfield:** the farthest star layer is FULL at the camera's zoom floor (every capital floor too) and tiles the whole viewport there; a new floor must keep both. Locks: `StarfieldBackground.test.ts`, `galaxyStarfield.test.ts`, `lodStarfield.coverage.test.ts`.
- **Zoom-in cap:** the camera never zooms in past the point where the piloted hull fits on screen (`zoomCeilingForView`); the follow camera has no look-ahead, so re-check the cap before adding one. Lock: `tests/unit/hullZoomCeiling.test.ts`. Detail for both: [ship-scale](../../docs/architecture/ship-scale.md#client-rules-in-detail).
- **Spectator:** `pilotMode` is the only store field; the free-roam camera pose lives in the renderer `Camera`, never the store. The death flip mounts no UI (the build palette is pre-mounted). While spectating, the own parked hull is never re-seeded or re-predicted from the schema. **Pilot swap** goes over the live room (no rejoin): despawn the local predWorld body and null the `Reconciler` so `welcome` re-anchors; the glide is a one-shot `Camera.glideTo`. Netgate required. Locks: `spectatorMode.test.ts`, `BottomControlPanel.test.tsx`, `spectateOwnHullDrawnPose.test.ts`, `ColyseusClient.spectateRace.test.ts`, `ColyseusClient.pilotSwap.test.ts`, `Camera.test.ts`. Detail: [spectator](../../docs/architecture/spectator-and-construction-mode.md#client-rules-in-detail).
- **Cinematic camera:** precedence is director > glide > follow > pan; the director reads rendered poses (never re-interpolates); keyframes never touch Zustand; overlay/HUD hiding goes only through `?cleanworld` / `?hud` and `SET_HUD_OVERLAYS`. Locks: `CameraDirector.test.ts`, `hudMode.test.ts`, `tests/e2e/cinematic-camera.spec.ts`. Detail: [cinematic-camera](../../docs/architecture/cinematic-camera.md#client-rules-in-detail).
- **Upgrades, level, mounts:** the client never predicts a stat upgrade — it re-anchors from the authoritative `statAlloc` via the shared `deriveStatMultipliers`. Ship level, activated mounts and structure level are slim snapshot fields mirrored at one site; mount geometry comes from the shared `resolveInstanceMounts`, never the wire. Netgate required. Locks: `localStatAlloc.test.ts`, `snapshotRemoteSync.shipLevels.test.ts`, `slots.dynamicMounts.test.ts`, `EntityStatsPanel.test.tsx`. Detail: [leveling](../../docs/architecture/leveling-and-upgrades.md#client-rules-in-detail), [weapon-mounts](../../docs/architecture/weapon-mounts.md#client-rules-in-detail).
- **Collision changes need an E2E:** any change to how obstacles or remote ships are synced, reset or lerped in `ColyseusClient.ts` ships with a `tests/e2e/` spec that fails if the change is reverted. Detail: [collision-layers](../../docs/architecture/collision-layers.md#client-rules-in-detail).
- **Every collidable entity is in predWorld:** a new entity the local player can collide with or shoot registers a predWorld body (prefixed id, spawn, `setShipState` per snapshot, despawn, tracked id set); the server iterates it in `advanceProjectiles`, `handleFire`'s hitscan and `applyDamage`. Never render remote ships from `remoteHistory`. Detail: same guide.
- **Pose-core entities construct through `ClientEntityFactory`:** an unrecognised kind returns `null` and is skipped; the swarm caches (`predSwarmKeys`, `_movingSwarmKeys`, `_swarmBodyKeyCache`, `_aiRegisteredIds`) stay in `ColyseusClient`, never the factory. Detail: [generic-entity-pipeline](../../docs/architecture/generic-entity-pipeline.md#client-rules-in-detail).
- **Y-flip:** game coords handed to the Pixi scene graph flip (`pixiY = -gameY`), but `art/fx` APIs that take "game space" flip themselves — never flip twice; never scale the warp filter centre by `renderer.resolution` (a phone-only renderer bug is a frame mismatch until on-device evidence says otherwise). Locks: `PixiRenderer.warpCenter.test.ts`, `navalShellBursts.test.ts`. Detail: [visual-effects](../../docs/architecture/visual-effects.md#client-rules-in-detail).
- **Halo radar:** `HaloRadar.update()` allocates nothing; its decisions stay pure and unit-locked under `halo/`; on-screen contacts are excluded at candidate build, never by a timer. Locks: `halo/*.test.ts`, `ring-indicator-*.spec.ts`. Detail: [off-screen-indicators](../../docs/architecture/off-screen-indicators.md#client-rules-in-detail).
- **Far-zoom icons:** keep `FAR_ICON.fadeStartPx` below a fighter's size at the spawn zoom. Locks: `FarZoomIcons.test.ts`, `tests/e2e/capital-helm.spec.ts`. Detail: same guide.
- **Warp burst:** exactly one flash per transit, on arrival (`warpEventFiresBurst`); never add a warp-out or spool-start burst. Lock: `PixiRenderer.warpBurst.test.ts`. Detail: [warp-visual](../../docs/architecture/warp-visual.md#client-rules-in-detail).
- **Pre-welcome guard:** any predWorld spawn in `syncMirror()`'s remote-ship branch is gated on `localId !== null`. Detail: [prediction-and-correction](../../docs/architecture/prediction-and-correction.md#client-rules-in-detail).

## Renderer worker boundary

On desktop the renderer runs in a Web Worker via `OffscreenCanvas`. How it works: [renderer-worker](../../docs/architecture/renderer-worker.md).

- **The wire format is [`render/worker/protocol.ts`](render/worker/protocol.ts):** structured-cloneable variants only — no DOM handles, Pixi handles or functions. Lock: `render/worker/protocol.test.ts`.
- **Forbidden imports inside `src/client/render/worker/**`** (CI-enforced): `react`, `react-dom`, `@mui/*`, `@emotion/*`, `zustand`. State crosses the boundary via the protocol.
- **`RenderMirror` is the per-frame wire payload:** any new field stays structured-cloneable.
- **`RendererFeedback` is a closed set:** a new field needs a phase-gate review (it grows every frame's postMessage) and is threaded through all three worker sites (`renderer.worker.ts` FEEDBACK post, `WorkerRendererClient.emptyFeedback`, its FEEDBACK handler). Pointer-cadence renderer state never goes to Zustand. Detail: [renderer-worker](../../docs/architecture/renderer-worker.md#client-rules-in-detail).
- **No `pixi-viewport` inside the worker** (no DOM): the worker uses the hand-rolled `Camera`, fed by pointer/wheel events forwarded from the main thread.
- **Fallback:** without OffscreenCanvas, `WorkerRendererClient` returns the main-thread `PixiRenderer`; production code never assumes worker rendering.
- **Touch devices default to the main-thread renderer** (`?worker=1` / `?worker=0` override). Don't flip the touch default back without a fresh on-device smoke measuring `raf_gap` clusters. Detail: [renderer-worker](../../docs/architecture/renderer-worker.md#history).
- **Galaxy map:** `GalaxyMapLayer` lives worker-side, driven by the `syncGalaxy*` messages; hover is a deduped `GALAXY_HOVER` back-channel sent only when the hovered sector changes. Galaxy poll hooks live in `app/`, never a top-level `src/client/galaxy/` dir (it collides with the `/galaxy` Vite proxy). Detail: [living-galaxy](../../docs/architecture/living-galaxy.md#client-rules-in-detail).
- **Galaxy landing reveal:** the opaque `galaxy-loading` gate waits for ALL badge sources (snapshot, presence, roster; the snapshot alone when logged out); every source is seeded at overlay install; each poll flips its loaded flag in `finally`, never only on success. Locks: `tests/e2e/galaxy-landing-reveal.spec.ts`, `useGalaxyStats.test.tsx`, `useGalaxyPresence.test.tsx`, `rosterPoller.test.ts`. Detail: same guide.

## Sizing default: start tiny, grow on request

When you build any new UI element — modal, panel, card, button, chip — **default to as small as humanly possible**. Especially on mobile. We will iterate it bigger when the user reports it's hard to hit or read; the reverse direction (shipping huge and shrinking back down) wastes review cycles and feels worse.

Concretely:
- Card silhouettes / icons: start ~24–36 px. Don't reach for 64 px without a reason.
- Body text in HUD / overlays / cards: 9–11 px. Captions 8–9 px. Reserve 12+ px for primary CTAs.
- Dialog `maxWidth`: prefer `xs`; only step up to `sm` if content genuinely needs it.
- Padding inside cards / dialogs: `p: 0.5`–`0.75` (4–6 px). Avoid MUI defaults (which are 16–24 px).
- Touch targets that absolutely must be 44 px (iOS HIG) — only fight for that on PRIMARY confirm actions, not every chip.
- Buttons: `size="small"` by default, with `fontSize: 11`.

The bias: it's easier to hear "this is too small, bump it 10 %" than to undo the visual heaviness of a default-sized MUI component cluster. The 2026-05-12 ship-picker rebuild is the canonical example — `maxWidth="sm"` + full kind descriptions + 64 px silhouettes + 22 px stat chips read as "absolutely huge" in playtest; the rebuild dropped to `xs`, 36 px silhouettes, a one-line stat readout, and 11 px buttons.

## Layout Slot System

In-game React overlays are positioned via **named slot anchors** ([layout/](layout/)), never hand-placed. Full story: [mobile-layout](../../docs/features/mobile-layout.md#client-rules-in-detail).

- **Anchors** live in [layout/anchors.ts](layout/anchors.ts). Adding one is fine; changing an existing anchor's CSS is a code-review prompt.
- **Widgets render via `<Slot anchor="...">`** and never set their own `position`, `top/left/right/bottom`, `zIndex` or safe-area insets; z-tiers come from [layout/zIndex.ts](layout/zIndex.ts) and only anchor hosts use them. (The structure placement banner is the one widget positioned over the world.)
- **Drawer:** never a `SwipeableDrawer` (its global touch listeners wreck mobile RTT); `keepMounted` stays on; snapshot-rate work in a drawer tab gates on `drawerTab === '<id>' && isDrawerOpen`.
- **Keep these surfaces:** don't delete the `HudTestAttributes` mirrors without auditing every spec that reads them, nor `ProfileModal.tsx` / `SettingsModal.tsx` / `AvatarMenu.tsx` (the desktop path).
- **Logout** has one definition, `useLogout()` ([auth/useLogout.ts](auth/useLogout.ts)); every logout entry point routes through it. Locks: `tests/e2e/avatar-menu-logout.spec.ts`, `useLogout.test.tsx`.
- **Orientation:** portrait works by default; landscape is opt-in via `<FullscreenToggle>`. Never reintroduce a first-gesture orientation lock or a portrait-block overlay.
- **Speed dial:** discrete tap actions go in the bottom-right `SpeedDial`; held controls (joystick, FIRE, BOOST) stay dedicated. Dial actions also bind `onTouchStart` (a second touch never gets a click) and drop the trailing synthesized click; a test opens the dial before clicking an action. Locks: `tests/e2e/speed-dial.spec.ts`, `tests/e2e/speed-dial-multitouch.spec.ts`.
- **Structure placement:** only the discrete `placementKind` lives in Zustand; the ghost pose rides `RenderMirror.pendingPlacementPreview`; pointer→world conversion stays in the renderer (it owns the `Camera`) and returns via `RendererFeedback`. Desktop click and touch Confirm share `commitChosenPlacement`; `contextmenu` cancels only for a mouse gesture. Structures draw `structureRenderVerts` (the collider's Y-flip), never raw points. Locks: `structure-placement-ghost.spec.ts`, `structurePlacementClient.test.ts`, `contextMenuPlacement.test.ts`, `spriteBuilders.test.ts`, `buildCategories.test.ts`. Detail: [structures](../../docs/architecture/structures-and-power-grid.md#client-rules-in-detail).
- **Grid render:** the placement preview runs the server's `canConnect`, allocates nothing per frame, and draws no line to another owner's structure; an owner shows as "you", their display name or "Unknown", never a raw playerId. ## Input Throttling Discipline (2026-05-06)

The client may suppress redundant input sends ONLY when both the current and previously-sent input states are **fully idle** (every control bit false). Any held key — thrust, turn, boost — must be re-sent every tick, with an additional 250 ms heartbeat in idle to keep the server's session alive.

Why narrowed to all-idle: when a held input has been throttled, the server's worker re-applies the held state each tick under its synthesised-ack contract (see [src/core/CLAUDE.md](../core/CLAUDE.md) → Input Queue Contract). When the client THEN sends a state change at a tick higher than the synthesised ack, the worker's max-tick-clamp jumps the ack past the intermediate ticks — silently skipping a physics step that the client's local prediction DID apply. On a fast-moving ship this surfaces as a ~8 unit drift per state-change event, with `corr` rate sticking around 20–30 %. Restricting throttling to all-idle frames is safe because held all-idle adds zero impulse — the server skipping a tick is physically equivalent.

**Rule:** any future per-tick stream that adds throttling needs the same audit: when the held state is "active" (changes physics), the server's queue must stay populated. See `docs/LESSONS.md` 2026-05-06 follow-up for the full incident.

## Multi-mount mirror surfaces (Phase 2c–4c, 2026-05-11)

The renderer mirror exposes per-mount data on three surfaces, all keyed by mount id (from the ship-kind catalogue):

- `ShipRenderState.mountAngles?: number[]` — per-mount slewed angle in arc-local frame, **indexed by catalogue mount-order** (`kind.mounts`). For the **local player**, populated each tick by `ColyseusClient.tickLocalMountAim` → `fcTickMountAngles` (predicted, aimed at each group's lock). For **remote players**, populated by the snapshot handler from `snap.states[id].mountAngles` (authoritative). Undefined ⇒ renderer falls back to `baseAngle`. **Catalogue-indexing is load-bearing AND was latently violated (2026-06-05 fix).** Both readers index by catalogue order — the live-beam direction (`localKind.mounts.findIndex(m => m.id === mountId)`) and the turret sprites (`shipSpriteUpdater` → `MountVisualManager.applyMountAngles(id, kind.mounts, mountAngles)`). The local writer `tickLocalMountAim` USED to size + index the array by the **active SLOT's** mounts (`localShipMounts()` = `resolveSlotMounts`, slot-local order) — correct ONLY while a slot is the full catalogue in catalogue order (true for every ship today, so the bug was latent). The write now goes through `fcTickMountAngles(angles, catalogueMounts, …)` (fire control; the former `combat/localMountAim.ts` helper is deleted): it writes catalogue-indexed, one entry per instance mount, each aiming at its group's lock. The moment a kind ships a slot that is a subset/reorder of `kind.mounts`, slot-local indexing made the local player's beams + turrets read the WRONG mount's angle (or `undefined` → base) — remote players were always fine (server writes catalogue-indexed).
- `SwarmRenderState.mountAngles?: number[]` — same field on drones. Populated only for **in-interest drones** from `snap.drones[].mountAngles`. Out-of-interest drones leave it undefined and their barrels render at `baseAngle` until they re-enter interest.
- `RenderMirror.liveBeams: Map<mountId, BeamData>` and `RenderMirror.remoteLasers: Map<shooterId, Map<mountId, BeamData>>` — per-mount beam state. The pre-2c single `liveBeam` and flat `remoteLasers` shapes are gone.

**Per-frame `mirror.ships.set()` rebuild MUST preserve `mountAngles`.** The local-ship update in `ColyseusClient.updateMirror()` and the remote-ship update in `syncMirror()` both reconstruct each ship's mirror entry from scratch (predWorld pose + lerp offset). Non-spatial fields need explicit `...(prev?.X ? { X: prev.X } : {})` preservation or they wipe at 60 Hz. The fields currently in this category: `kind`, `displayName`, `mountAngles`. Adding any new non-spatial field to `ShipRenderState`? Add it to BOTH rebuild sites or it disappears silently.

The visible bug when this rule was broken: the local player's interceptor showed two correctly-rotated wing beams via the one-shot ghost projectile path (which carries pre-computed endpoints) but the continuous `liveBeam` rendered straight forward — because the renderer re-derives beam direction from `mirror.ships.get(localId).mountAngles` each frame, and that field was being wiped between `tickLocalMountAim`'s write and the renderer's read.

`MountVisualManager` ([src/client/render/MountVisualManager.ts](render/MountVisualManager.ts)) owns per-mount Pixi `Graphics` (turret sprite + dotted aim line). One cluster per ship sprite (player AND drone), pooled across the ship's lifetime. The `applyMountAngles(shipId, mounts, angles?)` method updates rotations each frame; undefined `angles` snaps every mount to baseAngle. Renderer despawn path calls `removeShip(shipId)` to free the cluster.

`BARREL_LENGTH = 20` deliberately matches the 20 u server-side self-hit clearance in `SectorRoom.handleFire`/`handleAiFire` so beams emerge from the *visible* barrel tip. Don't change one without the other.

The aim-line preview is drawn as a dotted chain (Pixi v8 `Graphics` has no native dashed stroke — we draw short segments manually). Its length is **per-mount, = the bound weapon's effective reach** via the pure `aimLineLengthForMount` (`render/aimLineLength.ts` → `weaponAutoFireRange`: hitscan→`range` e.g. 250, projectile→0.85× max travel, missile→0.5× max travel). It used to be a hardcoded 500 for every mount, so the interceptor beam (range 250) drew its guide at 2× the actual reach (R2.14, 2026-06-12). `6 u on / 4 u off`, alpha 0.25; the dash chain rotates with the parent mount container; no per-frame redraw. Lock: `aimLineLength.test.ts`.

See [docs/architecture/weapon-mounts.md](../../docs/architecture/weapon-mounts.md) for the call-graph and the "do not add a second correction path" rule.

### Beam length is `scale.x ÷ texture.width`, NOT `scale.x = worldLen` (Equinox laser issue, 2026-06-14)

`BeamSpritePool` draws each beam segment as a stretched `Sprite`. A Pixi sprite renders `worldLen = scale.x × texture.width`, so the world length must be set as **`scale.x = worldLen / texture.width`**. The solid core uses the 1×1 `Texture.WHITE` (÷1, fine), but the **gradient + fade textures are 256 px WIDE** (they have to be — that's where the horizontal fade lives). Setting `scale.x = worldLen` on those rendered the fade tail **256× too long** (a 75 u tail → ~19 200 u): the "fade" stretched off any screen at any zoom, so in empty space the beam looked SOLID to infinity and "never tapered" — the long-standing "laser renders infinitely / flies off the screen" bug. **Headless unit tests fall back to `Texture.WHITE` (1×1) for the canvas textures, so they could NEVER see this** — the fix had "passed" four rounds of screenshots while staying broken on-device. Lock: `BeamSpritePool.solidTaper.test.ts` now injects a genuine 256-px `Texture` and asserts the DRAWN world length (`scale.x × texture.width`, exposed by `solidLenAt`/`fadeTailAt`) equals the intended length. **The damage falloff is LINEAR + bounded at `range × maxRangeMul` (interceptor 250 → 325); the matching visual is solid to `optimalRange × VISUAL_BEAM_SOLID_FRAC` (`ColyseusClient`, default 0.4 = inner 100 u) then a long gradual fade to nothing at maxRange — purely visual, `solidDist` never feeds damage.** Verified end-to-end (no-hit empty-space + hit cases) by `tests/e2e/laser-falloff-probe.spec.ts`, which forces `?zoom=` for a deterministic capture (the spawn camera-zoom ease otherwise lands before/after screenshots at different scales — a real comparison trap that masked the bug, see `docs/LESSONS.md` 2026-06-14).

## Game time on the client (time scale stream)

- `ColyseusClient.gameClock` (a core `GameClock` over the injected `clock`) is the sector's game time. Its speed is set ONLY from the snapshot's `timeScale` keyframe (absent = 1×, #16).
- **Everything that turns time into TICKS uses it:** the clock anchor (`clockAnchorPerfNow` is GAME ms), `targetTick`, the render tick phase / dead-reckon (`_lastLocalTickAtMs`, game ms; a RAF wall timestamp goes through `gameClock.at(wallMs)`), and the shell display tick.
- **Wall time stays for:** networking (wire-arrival intervals, RTT), stall detection (`_anchorFreshAtMs`), diagnostics and UI.
- **A speed change keeps the anchor.** The game clock is continuous across a change, so the (serverTick ↔ game ms) anchor stays valid and the normal eased anchor update absorbs the small timing difference. The server GLIDES speed changes (the dimmer), so each step is small. No `fromTick` arithmetic; the shared contract is "60 ticks per GAME second" on both sides.
- At 1× `gameClock.now()` / `.at(t)` return the wall value EXACTLY (byte-identical until the first speed change).
- Lock: `ColyseusClient.timeScale.test.ts`.
- **Display delays are GAME ms (4b).** The swarm floor/ceiling is 100/speed .. 280/speed wall ms (`setSwarmDisplaySpeed`); missiles use `MISSILE_DISPLAY_DELAY_MS / mirror.timeScale`. Arrival stamps stay wall. This keeps the window ~6 poses at every speed, inside `POSE_RING_DEPTH`. Lock: `swarmInterpolation.timeScale.test.ts`.
- **World motion between snapshots uses GAME frame time.** A per-frame step that moves the world (projectile extrapolation, ghost bolts, the drawn turret slew) takes `gameFrameMs()` (`lastFrameMs` × speed), never `lastFrameMs`. Visual error smoothing (reconciler lerp, offset springs) stays on wall time. The lint wall cannot see a `dt` variable, so this is a review rule; it was missed once and slow motion looked ~25 % calmer instead of 2.5× (hostile review 2026-11-12). Lock: `ColyseusClient.timeScale.test.ts` "a projectile is extrapolated by GAME time".
- **Presentation follows the speed from ONE source (4c).** `RenderMirror.timeScale` (absent = 1×) reaches the renderer on both paths. `PixiRenderer.fxNow()` (a `GameClock` over `performance.now()`, speed set at the top of `update`) is the time EVERY effect and animation reads: explosions, beams, recoil, connector pulses, shields, fences, lights, the backdrop, the effects service tick and the incoming-fire countdown (game seconds).
  - A NEW effect must take its time from `fxNow()` (or the `now` it is handed). `src/client/render/**` and `src/client/effects/**` lint-ban `performance.now` / `Date.now` outside a real-time allowlist in `eslint.config.js`.
  - Real time stays for pose interpolation against wall-stamped arrivals, the camera and UI (warp curtain, radar, lock marks, health-bar fades, selection) and cost measurement. Inline `-- real time: <why>` lines in PixiRenderer.
  - Lock: `FxExplosions.timeScale.test.ts` (an unmodified effect driven by a 0.5×/2× clock lives 2× / 0.5× as long in wall time).

## Phase A3 — Renderer decision logic extraction (2026-05-13)

Per-entity sprite-update decisions (create / rebuild / reposition / skip) live in `src/client/render/spriteUpdateDecisions.ts` as pure functions, NOT inlined inside `PixiRenderer.ts`. The Pixi calls (Graphics instantiation, `addChild`, `tint`, `alpha`, `destroy`) stay in the renderer; only the branching lives in the pure module.

**Why**: the Phase 6b "lingering hull permanently invisible" bug was a too-aggressive `if (!ship.kind) continue;` skip in the renderer that left the sprite uncreated forever when the schema diff with `kind` arrived late. A unit test on a pure decision helper would have failed loudly: "no cache + unknown kind should `create` with the fallback kind, not `skip`." The extraction makes that contract explicit and testable.

**The rule**: when you add a new entity-update method on the renderer (`updateXxx` taking `RenderMirror`), the per-entity decision logic MUST live in `spriteUpdateDecisions.ts` with unit tests covering every branch + a property-based test (fast-check, already installed). Don't inline new decision branches in `PixiRenderer.ts`.

Current functions:
- `decideLingeringSpriteAction({ cached, currentKind, fallbackKind })` — Phase 6b lingering hulls. Falls back to `fallbackKind` when `currentKind` is undefined and there's no cache hit (don't lock in the wrong silhouette but also don't go invisible).

Recovery thresholds are 2 ms lower than the downshift trigger AND require a 3× longer hold to prevent flicker. EMA alpha = 0.06 (~16-sample / ~270 ms response). Warmup = 8 samples held at `high`.

**Push-vs-pull discipline:**

- Per-frame metrics are fed to the budget by `EffectsService.tick`. Per-effect modules **pull** the resolved quality via `EffectsService.getQuality()` each frame (pull avoids per-transition allocations).
- The main-thread `PerfMonitor` (M9) computes `rafGapMs` EMA separately and pushes via `SET_EFFECT_QUALITY` **only on its own tier transition** (≤ once per 500 ms). NEVER per-frame. Lock: `EffectsBudget.test.ts` "100 frames at constant load → exactly 0/1 transitions".
- The budget keeps the more-restrictive of (locally-resolved tier, pushed tier) via `pickMoreRestrictiveQuality`. Pushed tier never weakens local resolution.

**Sector handoff (M9 wiring landed):** `EffectsService.resetForSectorHandoff()` is called from `ColyseusClient.resetPredictionState()` via the `onSectorHandoff` callback (sibling line to `rearmJoinReadiness()` — SRP per zone). The renderer's `resetEffectsForSectorHandoff()` method wipes per-entity continuous emitters + in-flight bursts + shield rings AND clears the diff trackers (`_activeThrustIds`, `_activeBoostIds`, `_activeShieldIds`) so the destination sector's first frame re-registers cleanly. `mirror.pendingEffectTriggers.length = 0` happens inside `resetPredictionState` for source-coord trigger drainage. Lock test: `src/client/net/transitResetEffects.test.ts`.

## Sector-to-sector trips are the loading screen (Phase 4 travel state)

- A transit never raises the curtain or `WarpScreen`: the store's `travelling` covers the trip, and `computeShowLoadingScreen` / `useWarpOrchestration` keep them down (HUD stays up). Only the first join uses the curtain.
- The trip is `ColyseusClient.stepTravel` (out → cruise → approach). It writes the local ship's mirror entry LAST in `updateMirror`, overriding prediction while it lasts.
- Nothing fades: the old sector is flown out of (the room swap waits for it), the new one is flown into. Never add a fade or a cut to hide loading; stretch the trip instead.
- A new jump of the local ship during a trip must add to `mirror.travelJumpX/Y` so the sky carries across it.
- Story: [docs/architecture/travel-state.md](../../docs/architecture/travel-state.md).
- **Art budget follows the device and each sector visit.** Touch devices get atlas pages by `navigator.deviceMemory` (`atlasOptsFor`: 4–14 pages; desktop 16 × 2048²). `setSector` starts a new art visit (`ArtService.newVisit`): new lit art packs into that visit's pages, and `PixiRenderer.collectUnusedArt` (every ~2 s) frees a past visit's pages once no sprite or gun holds or shows its art. When the budget is tight, art still in use is re-packed from the bake cache into the current visit (a copy that won't fit leaves the original in place). Sprite helpers re-acquire a handle marked `stale`; guns switch to `handle.next` when it is ready. Effect textures (group 0) are never freed. Lock: `tests/unit/artSectorCollect.test.ts`.

## GPU-lit art (default for players; Settings → Graphics → Lighting)

- Lit maps pack into **data** atlas pages (no premultiplication) that share the ordinary atlas's page budget; never put them on a canvas page.
- Every lit mesh registers with `litPass`; effect lights go into `litPass.scene` during `update()`, or are pinned to the sprite that draws the effect (`attachLight`). The pass lights everything once in the ticker before render. Keep it alloc-free.
- Players get a live level by default (desktop High, phones Medium/Low); automated browsers get Baked unless `?shiplight=` asks. The Baked level must stay byte-identical to the old baked look. Story: [docs/architecture/gpu-lit-ships.md](../../docs/architecture/gpu-lit-ships.md).

- **Composite ships**: `buildCompositeShipGfx` (`render/pixi/spriteBuilders.ts`)

  (`case SWARM_KIND_SCRAP`). It is a convexHull predWorld collider
  built from the parent kind's component collider

  `x*scale,-y*scale` — IDENTICAL to the server `ScrapSpawner`), in
  `SCRAP_COLLISION_GROUPS`. **It is DRONE-like, NOT asteroid-like (Phase-5
  desync fix, 2026-06-14):** spawned **UNLOCKED** at the server's
  `SCRAP_DEFAULT_MASS`. Its body follows the remote-entity anchor like a drone
  (latest server state each snapshot, stepped on the predicted timeline — see
  the one-paradigm rule above), so the local player's predicted shove matches
  the server's dynamic mass-1 scrap; its sprite joins the `=== 1` drawn-pose
  path in `updateMirror` + `swarmSpriteUpdater` (`resolveEntityDisplayPose`,
  not a second render-now `interpolateSwarmPose`). **Locking it (the old asteroid-like behaviour)
  made it an infinite-mass wall the player bounced off in prediction while the
  server let them shove it — every snapshot reconciled that divergence as the
  user's "huge spike in corrections".** `buildScrapGfx(parentKind, componentIndex)`
  renders the component's recentred sub-shapes from the catalogue, keeping the
  part colours so a dead ship visibly comes apart. `swarmSpriteUpdater` has a

  `(parentShipKind, componentIndex)`. Lock: `scrapClientLeaf.test.ts` (a ship

## Machined art (plan iridescent-seeking-rainbow)

- **Where it lives.** `render/art/` generates the Machined look from the ship and structure catalogue at load time: `fields` (shape), `shade` (light), `bake` (whole bakes as plain data), `bake.worker` (off-thread), `bakeStore` (IndexedDB cache), `atlas`. It is pure and DOM-free except `atlas`. The dev-only lab (`__art-lab__/`) is its visual test bench. Story: [docs/architecture/art-direction.md](../../docs/architecture/art-direction.md).
- **Bump `FORGE_VERSION` whenever the forge's output changes.** Players' devices cache baked art under it; a change without a bump serves stale art. `tests/unit/machinedArt.test.ts` pins a reference-bake hash to the version and fails until both are updated together.
- **`ArtService` is how the renderer gets art** (A2). Ask by kind, get a reused handle back at once (`pending` → `ready` | `failed`); keep the handle and check it per frame (no allocation). Bakes run on a worker pool (inline if workers can't start), come from the IndexedDB cache when possible, and are packed into the atlas within a per-frame budget (`tick()`). A `failed` handle (bake error, or over the texture budget) means the sprite keeps today's look. Phones get 2048² pages, budget 6; desktop 4096², budget 4. Structures bake per quarter turn (`rot`), so turning one never turns its sunlight. Which look draws is resolved ONCE on the main thread (`resolveArtMode`, `art/artMode.ts`): `?art=classic|machined` wins, then the player's per-device choice (Settings → Graphics, localStorage `eqxArtStyle`), then automated browsers (`navigator.webdriver`) get classic (so CI bakes never skew the netgate or slow the suite, the WebRTC precedent), else **Machined** (the default since A5). The result reaches the renderer through its constructor and the worker through BOOT (`artMode`/`artDelayMs`). Specs that test the look must pass `?art=machined`. Locks: `tests/unit/artService.test.ts`.
- **Ships (A3).** Player ships, drones and lingering hulls go through `art/shipArtSprites.ts` (`shipHandleFor` / `shipArtSwap` / `buildArtShipSprite` / `updateArtShipLight`), the ONE place a ship sprite switches between today's `Graphics` and a `MachinedShipSprite` (two Sprites cross-fading the two nearest baked sun frames, `machinedShipLight.ts`). The swap decision is the pure `decideArtSwap` (`spriteUpdateDecisions.ts`). Sprite maps are `Map<string, Container>`: never assume a ship sprite is a `Graphics`. A patrol bakes its faction paint, so a Machined patrol is never tinted (damage flash still is). The render worker gets the page query string on BOOT (`search`), because it has no `window`. DEV hook `__eqxArtStats` (`?worker=0`) is re-assigned every frame so it follows the LIVE renderer (a dev StrictMode remount leaves a disposed one). Test trigger: `?artDelayMs=` holds bakes back. Locks: `swarmSpriteUpdater.machinedArt.test.ts`, `machinedShipLight.test.ts` (+ `.heapDelta`), `decideArtSwap` cases, `tests/e2e/machined-art.spec.ts`.
- **Structures, scrap, asteroids (A4).** Same helper module: `structHandleFor` (bakes the quarter turn, so the sun stays put when a structure is rotated), `scrapHandleFor` (one bake per `(parentKind, componentIndex)`, from `shipScrapGroups`; tumbles, so ship-style cross-faded frames), `rockHandleFor` (per asteroid, from the server's seeded outline; its turn is taken once when first seen, never re-baked as it turns). Structures and asteroids draw a `MachinedFlatSprite` (one lit frame); their children (readouts, rings, barrels) are rebuilt on it by the create path. A Machined asteroid bakes its resource colour, so it is not tinted.
- **Warm-up.** When the art service starts (on the galaxy map, before a sector is joined) the renderer queues `warmUpJobs()` (`art/warmUp.ts`: every regular ship kind, then the common structures). Warm-up bakes are LOW priority: anything a sprite asks for goes to the front of the worker queue, and a queued warm-up bake is promoted when a sprite asks for it. Packing (`ArtService.tick`) runs from the Pixi ticker, not `update()`, so it also runs on the galaxy map and warp screens where `update()` doesn't.
- **New effects and backdrop (plan iridescent-seeking-rainbow v3).** Effect textures are `fx` bake jobs (`art/fx/fxTextures.ts` registry `FX_SPECS`), asked for with `ArtService.fx(id, variant?, seed?)`. **Bump `FX_VERSION` with any generator change** (lock: `fxTextures.lock.test.ts`). Wrapping textures get their own texture (`Atlas.standalone`), the rest share the atlas; flipbooks are cut with `flipCells`. Switch: `resolveFxMode` (B6): ON for players whenever the art is Machined (the one "Detailed art" setting covers both), OFF for automated browsers (`navigator.webdriver`), `?fx=new|classic` wins; carried to the worker on BOOT (`fx`). Specs that test the effects pass `?fx=new`. Per-frame effect maths lives in `art/fx/fxMath.ts` (pure, heap-delta locked). A laser on a shield is a held contact (`ShieldContacts`), never a stream of hits. **Backdrop (B2):** `art/fx/Backdrop.ts` takes over from `StarfieldBackground` once its star tiles are ready (the old field is the fallback, never removed while `?fx=new` is off); its nebula follows `IRenderer.setSector` (worker: `SET_CURRENT_SECTOR` also calls `renderer.setSector`). **Weapons (B3):** `art/fx/FxWeapons.ts`: `FxBeams` draws glow + flowing strip + muzzle/hit flares OVER today's beam pools (which stay the core and keep the solid-then-fade contract and the drawn-origin feedback); remote beams pass their `hit` flags. `FxProjectiles` replaces bolt/tracer Graphics with pooled sprite views (released by generation stamp; pulse orbs and beams keep today's shapes).
